## ✨ 核心特性

- 🖥️ **Playwright / Chromium 真机拟人引擎 (全新 v1.4.0 重大升级)**：
  - 彻底抛弃纯 HTTP GET 的易风控搜索方式，引入真正的无头浏览器内核；
  - 模拟真实键盘输入事件流 (`keydown`/`keypress`/`keyup`)，带 50~120ms 随机按键延时与自动补全触发；
  - 模拟回车提交与鼠标滚轮向下浏览搜索结果，100% 触发微软官方反欺诈遥测，彻底免疫“搜索暂停 / 15分钟冷却限制”；
  - **用完即焚极速释放**：仅在搜索期间唤醒浏览器，任务结束立即关闭释放，平时常驻内存低至 ~60MB。
- 🕒 **4 时段错峰离散作息排程 (6-10 / 10-14 / 14-18 / 18-22)**：
  - 针对单个家庭 IP 最多 4 账号的黄金安全阈值，预设 4 个错峰作息窗口；
  - 支持自定义开始时间（结束时间自动计算 +4 小时），区间内注入 0~60 分钟随机泊松延时；
  - **单账号搜索拉长至约 2 小时**：平均每 3.5 ~ 4 分钟检索一次，极致模拟人类上班摸鱼作息。
- 🖥️ **无头浏览器实时状态监控卡片**：
  - Web 控制台直观呈现当前无头浏览器运行动作（打字中、呼吸休眠倒计时、当前检索词、内存占用 MB）。
- 🔍 **单次安全验证搜索**：
  - 提供一键「单次测搜」功能（15秒单次输入验证增分，完全避免触发频率惩罚）。
- 👥 **多账号矩阵管理与一键切换**：
  - 各账号独立凭据、环境严格隔离，日志全量标记 `[账号名]` 规范前缀。
  - **上下文串号修复 (v1.5.2)**：执行期间锁定账号上下文，WebUI 的同步/体检/测搜不会再把 Cookie 或 Token 抢到别的账号，Token 也不再跨账号回退。
- 🧩 **任务区打孔卡自动推进 (v1.5.2 新增)**：
  - 自动识别「任务」区的每月/每周打孔卡（如「十月必看五大亮点」），每天解锁一项后自动完成当日可做的任务；
  - 每天只推进一次，避免重复打开任务页增加风控暴露面。
- 📌 **任务进度不再“猜” (v1.5.3 修复)**：
  - 「双端签入」「每日活动集」改为以官网连签任务真实状态为准，官网说没完成就会把误标的「已完成」纠正回来，并在卡片上直接显示「官网 App 连签 X/7 天（今日已签/未签）」；
  - 「最后更新」时间不再恒为 `--`；
  - App 签到未生效时会明确提示是 Token 失效还是移动端授权绑错了账号。
- 🎯 **数据可信度与健壮性重构 (v1.6.0)**：
  - **「今日已增积分」改用官网「今日积分」真实值**（取不到时回退到「当前余额 − 今日起始余额」），彻底废弃「各任务积分求和」的口径——旧口径实测会虚高几十点；
  - **历史图表的任务明细改为真实分解**（由各任务实际积分生成），删除按固定模板编造的「签到10/阅读30/搜索(earned-80)/活动集30/Quiz10」；
  - **不再无条件给分**：每日活动集、活动卡片只在真正完成/领到时才记分，不再出现「什么都没做也显示 +40」；
  - **「每日活动集」「桌面端打孔卡」成为真正独立的开关**（旧版这两个开关后端根本不读），并删除无用的 `quiz`/`searchSpan` 配置；
  - **单账号异常不再拖垮其它账号**：逐个账号隔离执行，失败账号会跳过并在报告里列出；
  - **「停止」按钮立即生效**：轻量搜索模式的等待改为 1 秒切片，不再需要等最长 20 分钟；
  - **Epic 领取与积分任务互斥浏览器资源**，避免两个 Chromium 同时跑把 NAS 内存打满；
  - **`data/app.log` 增加 5MB 轮转**，「全部日志」改为只读文件尾部，不再整文件读入内存；
  - **history.json 改为内存缓存 + 延迟合并落盘**，消除每次任务进度更新都全量读改写「账号数+1」次的写放大；
  - **新增单元测试**（`npm test`，23 个用例覆盖账号上下文隔离、解析回归、历史分解、调度计划）。
- 🧬 **浏览器指纹一致性 (v1.6.1)**：
  - 指纹常量收敛到 `src/core/fingerprint.js` 单一来源，UA / 客户端提示 / 平台三者不再各写各的；
  - Playwright 路径用 CDP `Emulation.setUserAgentOverride` 把 **UA、`Sec-CH-UA`、`navigator.platform`** 一次性对齐，消除「UA 说 Chrome 131、客户端提示说真实版本、platform 说真实系统」这种三处互相矛盾的情况；
  - 纯 HTTP 路径补齐真实浏览器一定会带的请求头（`Accept`、`Accept-Language`、`Sec-CH-UA*`、`Sec-Fetch-*`、`Upgrade-Insecure-Requests`、`Priority`），不再只发一个孤零零的 UA；
  - 去掉会在 `navigator` 上凭空造出自有属性的 `webdriver` 覆写（真实浏览器没有这个自有属性，反而更显眼）；
  - WebGL 由 SwiftShader 软件渲染改为常见核显标识，避免无头环境的软件渲染特征；
  - 启动时若镜像内 Chromium 主版本与指纹常量脱节会打印提醒，不会静默产生版本矛盾；
  - 新增 `test/fingerprint.test.js` 专门防「前后不对称」回归。
- 🥷 **反检测与稳定性升级 (v1.6.2)**：
  - **浏览器驱动换成 patchright**：Playwright 最容易被识别的特征不是 `navigator.webdriver`，而是 CDP 的 `Runtime.enable` / `Console.enable` 泄漏和 `--enable-automation` 启动参数。patchright 是 Playwright 的补丁分支（API 完全一致），从协议层把这些抹掉了；
  - **每个账号持久化浏览器会话**：Cookie 与 localStorage 跨次复用，不再是「一个全新浏览器里凭空出现登录态」。写回时剔除 `_U` 身份 Cookie，并绑定账号凭据指纹 —— 换账号或重新登录后旧会话自动作废，杜绝串号；
  - **搜索停滞保护**：连续 N 次搜索官网进度不涨就主动停手（默认 10 次，可在配置中心调整）。当天搜索额度已到顶时不再空跑，既省执行窗口，也减少风控暴露面；
  - **单元测试增至 41 个**（新增会话持久化与停滞保护回归）。

## 🚀 极速部署指南

### 方法 1：使用 Docker Compose 部署（推荐，群晖/威联通/极空间/VPS）

1. 在服务器或 NAS 上创建一个项目目录，例如 `ms-rewards`：
```bash
mkdir -p ms-rewards && cd ms-rewards
```

2. 在该目录下创建 `docker-compose.yml` 文件：
```yaml
version: '3.8'

services:
  microsoft-rewards:
    image: ghcr.io/saarjoye/microsoft-rewards-docker:latest
    container_name: ms-rewards
    restart: unless-stopped
    ports:
      - "5308:5308"
    environment:
      - TZ=Asia/Shanghai
      - PORT=5308
    volumes:
      - ./data:/app/data
```

3. 启动容器：
```bash
docker compose up -d
```

4. 启动后，打开浏览器访问：`http://<NAS或VPS的IP>:5308`，即可进入现代化控制台！

## 💡 小白 1 分钟配置上手指南

初次打开 Web 控制台时，点击右上角的 **「💡 新手配置向导」**，跟随引导仅需 3 步：

### 步骤 1：移动端授权 (OAuth Token)
1. 点击向导中的 **「🔑 打开微软官方登录授权页」**，在弹出的微软官网登录你的账号；
2. 登录同意后，浏览器会跳转至类似 `https://login.live.com/oauth20_desktop.srf?code=M.C508_...` 的地址；
3. 将地址栏中的完整 URL 复制粘贴到输入框中，点击 **「一键换取并保存 Token」**。
> ✨ 提示：系统会自动捕获并持久化保存 Refresh Token，后续系统会**永久自动无感续期**，无需再次操作。

### 步骤 2：网页端 Cookie 配置
1. 在电脑浏览器登录 [cn.bing.com](https://cn.bing.com/)（必须使用与 OAuth Token 相同的微软账号）；
2. 按 `F12` 打开开发者工具，在【网络 / Network】中抓取任意请求的 `Cookie`，或者直接在【应用程序 / Application -> Cookies】中复制完整 Cookie 文本；
3. 完整 Cookie 必须包含 `_U`。`KievRPSSecAuth` 不能替代 `_U`，否则 PC 搜索无法关联计分；
4. 粘贴至输入框，点击 **「测试 Cookie 有效性」**。系统会验证 Cookie 登录态，并在已配置 OAuth Token 时自动核对两者是否为同一微软账号；身份无法确认时不会误报为一致。

### 步骤 3：网络与代理（若在境外 VPS 部署必选）
- 如果你的设备在**中国国内家庭宽带 / NAS**：保持默认直连即可。
- 如果你的设备在**境外 VPS**：
  1. 勾选 **「启用网络代理」**；
  2. 填写国内代理节点地址（如 `http://x.x.x.x:7890` 或 `socks5://x.x.x.x:1080`）；
  3. 点击 **「一键检测出口 IP 与地区」**，确认出口归属为 **中国大陆 (CN)**，防止因海外 IP 导致微软账号被锁区或异常。

配置完成后，点击 **「▶️ 立即执行」**，即可在控制台实时看到打卡日志与积分上涨！

## 🧬 浏览器指纹与反风控说明

自动化最容易出问题的地方不是「伪装得不够像」，而是**前后不一致**——同一个请求里几个字段互相打架。
本项目在 v1.6.1 做过一次完整排查，结论如下。

### 指纹的单一来源

所有身份常量集中在 `src/core/fingerprint.js`。UA、客户端提示（`Sec-CH-UA`）、`navigator.platform`
三者由同一份常量派生，不允许各模块自行硬编码——历史上正是因为各处硬编码不同版本，
出现过「UA 说 Edge 131、客户端提示说真实版本、platform 说真实系统」这种三处矛盾。

升级基础镜像后如果 Chromium 主版本变了，启动日志会打印提醒，需要同步更新该文件里的 `CHROME_MAJOR`。

### 两条通道的身份是分开的（这是正确的）

| 通道 | 身份 | 说明 |
| :--- | :--- | :--- |
| Playwright 浏览器 | Windows + Chrome | PC 搜索、打孔卡、单次测搜 |
| 移动端 DAPI | Android + BingSapphire App | App 签到、新闻阅读 |
| 桌面客户端任务 | macOS + MSRewards/Desktop | 桌面专属打孔卡 |

移动端和桌面客户端的请求**不应该**带浏览器头——它们本来就是 App 客户端，带浏览器头反而更可疑。

### 为什么是 Chrome 而不是 Edge

镜像里安装的是 Debian 的 **Chromium**。Edge 与 Chromium 的版本号并不同步
（Debian chromium 已到 150 时，Edge Linux stable 才 143），声称 Edge 会引入
「声称了一个不存在的 Edge 版本」这种新的矛盾。Chrome 与 Chromium 同引擎、同版本号，
是代价最小的自洽选择。

**那容器里装真正的 Edge 会不会更好？** 实测数据：

| | Chromium (Debian) | Microsoft Edge (Linux stable) |
| :--- | :--- | :--- |
| 安装后占用 | ~267 MB | ~607 MB |
| 下载体积 | ~73 MB | ~172 MB |
| 依赖 | 43 个 | 37 个 + 需引入微软 apt 源与签名密钥 |

结论：装 Edge 只解决「品牌」这一项矛盾，**版本矛盾与系统矛盾依然存在，TLS 指纹也不会因此改变**，
却要多付约 340MB 镜像体积和一层外部依赖。所以默认不装；需要时可以通过环境变量
`CHROMIUM_PATH`（Dockerfile 里默认指向 `/usr/bin/chromium`）自行指向容器内的 Edge 可执行文件。

### 驱动层：patchright 与会话持久化（v1.6.2）

上面几条解决的是「字段自相矛盾」，但还有一个更硬的识别点：**自动化驱动本身**。
Playwright 启动 Chromium 时会启用 CDP 的 `Runtime.enable`，页面只要给 `console.debug`
挂一个 getter 就能探测到 CDP 的存在——这跟 UA 写得多像没关系。

v1.6.2 把驱动换成了 [patchright](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)
（Playwright 的补丁分支，API 完全一致），它从协议层修掉了 `Runtime.enable` /
`Console.enable` 泄漏，并去掉 `--enable-automation` 启动参数。

同时，每个账号的浏览器会话（Cookie + localStorage）会加密权限（0600）落盘到
`data/sessions/`，下次执行直接复用，浏览器看起来始终是同一台机器，而不是每次都是
「刚装好的浏览器 + 突然出现的登录态」。两条安全约束：

- 写回时**剔除 `.bing.com` 的 `_U` Cookie**：它是账号身份标识，上一轮残留的旧值一旦被
  带进下一轮就会串号或被重定向到登录页。配置里的 `_U` 每次启动都会重新注入，不影响计分。
- 会话**绑定账号凭据指纹**：Cookie/Token 换成别的账号后，旧会话直接作废，不会把 A 账号的
  浏览器状态带到 B 账号上。

### 仍然无法消除的差异（如实说明）

- **TLS / HTTP2 指纹**：纯 HTTP 通道走的是 Node 的 OpenSSL，与 Chromium 的 BoringSSL 不同。
  这不是改 UA 或请求头能解决的，只有真正用浏览器发请求才能一致。
- **渲染与硬件特征**：无 GPU 环境只能软件渲染，本项目把 WebGL 标识改成了常见核显，
  但更深层的渲染差异无法完全消除。
- **行为特征**：请求节奏、鼠标轨迹等属于另一层检测，本项目只做了基础的随机化与限速。

一句话：**这些手段能消除「自相矛盾」这种廉价识别点，但不能让自动化变成真实用户。**
真正决定账号安全的是地区、频率与行为是否克制。

## ❓ 常见问题 (FAQ)

### Q1：为什么提示“非中国大陆 IP，已自动停止”？
**答**：微软 Rewards 会严格检测用户 IP 地区。如果是中国区账号但在境外 IP 上打卡，极易被微软风控（封号、无法兑换礼品卡、任务跳区）。为保护您的账号安全，程序默认启用了国区安全锁。境外 VPS 用户请在配置中心开启代理并走国内节点。

### Q2：网页端 Cookie 会过期吗？需要经常更新吗？
**答**：微软网页 Cookie 通常有效期长达数周至数月。移动端的 OAuth Token 则由程序通过 Refresh Token 自动在后台刷新续期，无需手动干预。若 Cookie 失效，控制台及推送通知会主动提示您重新抓取。

### Q3：如何备份我的配置数据？
**答**：所有配置文件、任务进度、统计历史与浏览器会话均保存在映射的 `./data` 目录中（包括 `config.json`、`stats.json` 与 `sessions/`）。更换设备时只需打包转移 `data` 目录即可实现无缝迁移。若想强制所有账号「重新登录一次」，删掉 `data/sessions/` 即可，不会影响任务进度与积分历史。
